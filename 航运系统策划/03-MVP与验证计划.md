# 03 MVP与验证计划

## 1. 范围和版本门槛

本章是制作提案，不表示已经实施、完成试玩或承诺发布日期。验收阈值与样本量均为内部筛选假设，不是行业标准。先验证驾驶和因果链，再制作完整视听；本次交付仅策划，不包含游戏代码或可玩构建。

### V0 纸面与操作灰盒

一个短航场景、两个普通目的地、一种货、三张可比较订单；完成接单、转向、减速靠港、结算、供需变化。不需要正式美术、完整船队或剧情。纸面先演算一条最佳线路在运输后发生变化，灰盒再检查开船是否舒服。

V0通过条件：能独立完成一单；能清楚看见下一单选择变化；重复航行不依赖催单计时仍有基本乐趣。若两轮简化后仍不成立，停止扩内容，回到规则层修改。

### P0 最小完整Game Off候选

| 模块 | 最小交付 | 明确不做 |
|---|---|---|
| 驾驶 | 转向、加减速、宽容泊区、碰撞反馈、安全复位 | 真实帆船物理、战斗、沉船 |
| 地图 | 四港、五连接、一组可选捷径 | 无缝开放世界、陆地行走 |
| 订单 | 三卡以内、普通货运、保底信件、锁价 | 多单堆叠、抢单倒计时、采购交易 |
| 经济 | 三货、供需、在途预留、清楚结算 | 大规模产业链、贷款、税务模拟 |
| 成长 | 两项小升级、最多三船 | 百船、抽卡、船员关系系统 |
| 船队 | 单次派单、自动抵达、待命、同市场影响 | 离线挂机、自动连刷、完整船间避碰 |
| 完整性 | 开场教学、短篇结尾、继续/重开、存档 | 长篇故事、账号、云存档、付费和广告 |
| 体验 | 音量、暂停、图标＋文字、最小英文说明 | 多端同时上线、复杂本地化 |

若范围超出制作能力，削减顺序：第三艘船 → 第二档升级 → 一条地图支路 → 可选捷径。保持“亲自接单开船、交货到账、一次升级、至少一艘助手、运输改变市场”的闭环，不能削成只有点击收钱的菜单演示。

### P1 只有P0通过才做

一类易损订单、一个局部风向或节庆事件、鼠标辅助航点、结尾更完整演出。P2长期扩展才考虑更多海域、船型、乘客与救援、百船经营；不因标题或参考作品存在这些内容就默认承诺。

## 2. 原型试验与失败标准

### T1 短航操控与节奏

同一地图提供三种惯性/靠港宽容参数，不同时改美术。先找2位不了解操作的人观察误解，再用6–8位新玩家测试。记录首次接单到到账、熟练后短单时长、从看到订单板到到账的完整交易时长、相邻两次结算的间隔、转向修正、靠港失败次数、卡住和主动重试。20–30秒验收不强迫玩家限时阅读，但不能靠排除反复读单或菜单负担掩盖真实节奏。

内部通过目标：首单多数人无需口头协助完成；熟悉后普通短单中位数落在20–30秒，较慢玩家仍可从容完成而不受罚；单纯泊区对齐不应占据航程的大部分。时间超标先缩距离、减菜单和改善靠港，不增加强制自动结算。

失败信号：玩家持续分不清船头方向，驾驶像等待条，或靠岸反复失败远多于选路判断。先修操作表达，不能用新船和金币奖励掩盖。

### T2 SHIFT因果理解

对同样的地图、货物、操作和初始总奖励，比较A版“固定订单报价”与B版“运输改变库存与后续报价”。两版都必须可完成；采用交叉顺序，避免所有人先玩A后玩B造成学习偏差。小样本只用于发现问题，不做统计显著性或市场成功宣称。

让玩家先预测：这单交货后，哪个港更缺这种货，下一单哪个方向更值得考虑？随后实际开船验证。不要先把标准答案讲给他，再统计“理解成功”。

内部目标：6人中至少4人无需提示能说出“我送货降低了这里的缺口”；至少3人在新状态主动改变路线，并能解释成本或返程影响。数据不达标先减少并行信息、强化前后变化；若两轮仍只有设计师能讲懂，简化供需为更清楚的少量需求档位，保留玩家行为的直接后果。

若去掉动态供需后路线选择和体验几乎不变，不能声称主SHIFT成立；应调整规则或重新讨论方向，而不是仅改作品简介。

### T3 防止固定航路统治

纸面穷举或表格演算至少20次连续交付，比较四种策略：只看单次毛价、只选最短航、固定双港往返、观察供需并安排两步路径。固定初始状态，记录当前位置、实际收入、航时、库存、在途与可接订单。

检查是否存在一种策略在所有初始情境和成长阶段都压倒其他策略；至少准备三组有不同合理选择的状态。无需强求每种策略同样强，但不能只做一张永远亮着的最优订单卡。

特别测试马赛—热那亚布匹/木材往返：连续补货后需求应下降或单量收缩，不能因退货/反向运输无限复制物资。高价路线转移要能用账本解释，不靠暗中提高其他路线奖励。

### T4 船队是否增添经营

同一中期存档分别加入0、1、2艘助手，记录每分钟手动驾驶时间、面板停留、每分钟派单操作次数、主动改派、总收入与助手占比。观察玩家是否更想开船，还是开始等助手收钱。

内部目标：助手收入约占中后期20%–35%；打开船队面板不应成为连续驾驶的主要中断。两艘助手让人忙于菜单时，先改为只留一艘或批量显示待命状态；不增加离线收益来解决无聊。

### T5 成长和结束

在不知道结尾条件的陌生玩家中检查：第一笔升级是否可感知，第一次买船是否自然出现，是否懂得下一项目标，是否能在约12–18分钟体验到完整成长。记录实际花费和选择，不能只按设计师最优路线计时。

若玩家因为多买升级导致购船拖延，改善价格与购船目标提示，不剥夺选择或强行发船。如果三船太长，两船结尾是允许的缩减，但必须保留从亲驾到调度的变化。

### T6 视听与可访问性

在静音、关闭晃动、小窗口、浏览器缩放和只用键盘条件下完成首单；检查不靠红绿也能识别港口、缺货与危险。开场音频未解锁不能阻止游戏；暂停/恢复不得叠加多份音乐。

## 3. 记录口径

测试前取得记录同意；公开测试报告仅保留匿名汇总，不上传可识别个人信息、录音或账号。记录最少字段：版本、设备/浏览器类别、测试条件、任务、开始/结束、结算/取消、碰撞、供需预测、实际选择和失败解释。

“认为好玩”与“独立理解规则”分开记录；被设计师提示后的完成标为辅助完成。小样本完成率不叫商业留存，5分钟重复玩不叫长期黏性，页面好评不叫系统已验证。

本版本的测试结果状态：**尚未实施**。规则样例已给出，可用于下一步纸面与灰盒验证；没有把设计目标填成实际结果。

## 4. 功能与边界验收清单

| 场景 | 预期结果 |
|---|---|
| 连续双击接单 | 只生成一张在途订单，只扣一次来源货 |
| 助手与旗舰争接同单 | 只允许一方成功，另一方得到清楚提示 |
| 途中打开菜单或切后台 | 世界、助手、事件一致暂停，恢复不补跑 |
| 两船同帧送同港同货 | 顺序确定，金币/库存/在途可对账 |
| 交货动画中刷新页面 | 已结算只读显示，不重复到账 |
| 取消、再接、重复取消 | 无额外货物、金币、周转或成就 |
| 目的港储量接近上限 | 已接货有预留空间，不凭空丢货 |
| 来源货不足或钱不足 | 按钮解释原因，失败不改变部分状态 |
| 订单失效时点击原卡 | 重新验证，不接错货或错港 |
| 港口暂时无实物货单 | 可选低收益信件继续游戏 |
| 卡在岸线或碰撞重叠 | 安全复位到已经过的水域，不瞬移交货 |
| 刷新读取途中存档 | 船和订单一致，不掉货、不重付 |
| 损坏存档/旧版本 | 明确提示并保留可恢复副本，不静默清空 |
| 清空进度/重开 | 二次确认，取消时进度不变 |
| 达成结尾后继续 | 不重复发奖励，不锁住驾驶与订单 |

这些是未来实现验收，不是当前全部已通过的报告。

### 建议任务拆分与依赖

1. 驾驶与泊区：先完成单场景输入、碰撞和复位，提供标准航时测量。
2. 订单与账本：依赖航时参考，完成锁价、在途预留、结算幂等和存档。
3. 市场与海图：依赖可靠账本，完成库存周转、行情解释和航路提示。
4. 升级与船队：依赖前三项，完成购买、助手单程状态和成长节拍。
5. UI与视听：围绕通过测试的动作补表现；不在规则仍变化时制作大套资产。
6. 质量与发布准备：贯穿全部阶段，最后核对构建、提交哈希、说明、来源和授权。

人名、职责与实际开始日期在实施前确定，不把未参与者写成已承诺负责。

## 6. 主要风险与应对

| 风险 | 早期证据 | 优先处理 |
|---|---|---|
| 短航只有重复走路 | 玩家只看金币，不看海面或转向 | 缩空航段、改善船感和靠港，不加更多数值 |
| 经济太复杂 | 无法解释一次送货的影响 | 减少同时显示信息，必要时改需求档位 |
| SHIFT只在文案里 | 动态版和固定版选择无差异 | 重做库存/地图取舍，停止增加装饰 |
| 固定线路刷钱 | 单一路径长期统治 | 检查生产消费、相邻订单和返程价值 |
| 自动化替代游戏 | 助手占比过高、玩家等钱 | 限助手、慢单程、保留手动货量与技巧奖励 |
| 成长拖长Jam体验 | 购第三船远超目标时长 | 下调目标或两船结尾，缩而不堆奖励 |
| 状态不同步 | 重复到账、负库存、取消套利 | 先修账本与持久化，暂停内容工作 |
| 既有工程泄露/资格问题 | 混入私库、无许可资产、旧作小改 | 独立公开范围审查，保留开发与复用记录 |
| 截止前上传风险 | 构建只在开发机能跑 | 提前冻结、干净环境测试、保留回滚版本 |

## 7. 制作前与发布前的决定

制作前需要确认主要平台、引擎/工具、可用人力，以及是否以此新方案进入原型。现有私有代码、素材能否复用和能否公开是两个不同问题，必须逐项确认。

正式参赛前需要确认新游戏源码公开范围、许可证、资产再分发与占位方案、AI披露、itch页面及提交动作。策划在公开GitHub发布不代替这些决定，也不意味着已经报名。

完成的定义是：陌生人可启动并完成短篇、因果链能解释、账本稳定、公开内容合法且范围明确，再由明确授权执行正式发布与赛事提交。
